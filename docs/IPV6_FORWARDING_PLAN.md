# IPv6 与跨地址族端口转发计划

日期：2026-11-14。基线：`main` / `f1a6016`（已发布 v2.0.0 之后的测试清理提交）。

状态：已在 `codex/ipv6-kernel-forwarding` 实现三种新增方向，版本为 v2.1.0 开发版。核心隔离、公网及真实重启验收已通过；逐项结果、环境和未覆盖边界见 [IPv6 验收记录](IPV6_VALIDATION.md)。本分支不修改已发布的 v2.0.0。

选型约束：用户已确认不使用常驻中继进程。排除 GOST、NGINX stream、Realm 等用户态数据中继，跨族方向改为评估 Jool 内核转换。允许命令行工具及 systemd oneshot 在配置、启动和恢复时短暂运行；业务流量不经常驻用户进程。

## 1. 目标与优先级

已确认三种新增方向全部纳入，优先完成两种 IPv6 入站场景。箭头表示客户端连接 VPS 的地址族 → VPS 连接目标服务器的地址族；响应必须沿对应连接返回客户端。

| 方向 | v2.0.0 行为 | 本分支实现 | 实施优先级 |
|---|---|---|---|
| IPv4 → IPv4 | 已支持 TCP、UDP 和端口段 | 保留现有 nft 路径，作为回归基线 | 必须保持 |
| IPv6 → IPv6 | 不支持 IPv6 转发目标 | nft 原生 IPv6 DNAT + 按规则限制的 masquerade | 第一优先 |
| IPv6 → IPv4 | 没有 IPv6 入站转发 | nft 同族引流 + Jool Stateful NAT64，转换后按需 SNAT | 第二优先，先验证组合路径 |
| IPv4 → IPv6 | 不支持 IPv6 转发目标 | nft 同族引流 + Jool 静态 BIB 发布 IPv6 端点，转换后按需 SNAT | 第三优先，本期包含，先验证组合路径 |

每种方向都支持单端口、同号端口段及不同号端口段的一一对应，继续同时提供 TCP 和 UDP。端口数量必须相等，例如 `10000-10002 → 20000-20002`。

本期使用 IP 字面量；域名/DDNS、通用 NAT64 网关、其他业务传输协议和透明保留客户端源地址不在本期范围内。跨族转换仍要求 VPS 具备入站族可达入口及目标族出口和路由；不能凭配置替单栈 VPS 增加另一种网络连接。

## 2. 实现路径

### 2.1 同地址族：扩展现有 nft 引擎

nftables 支持 IPv6；`inet` 表自 Linux 5.2 起支持带 `ip` / `ip6` 地址族标记的 NAT。本项目的限制目前在目标校验和规则生成，而不是 nft 无法处理 IPv6。[官方 NAT 文档](https://wiki.nftables.org/wiki-nftables/index.php/Performing_Network_Address_Translation_%28NAT%29)

- IPv4 → IPv4 保持原路径，IPv6 → IPv6 生成相应的 `dnat ip6` 规则，正确处理 `[IPv6]:端口` 和端口映射。
- 继续只匹配发往本机地址的入口流量；本机访问自己的非回环地址也需支持，不劫持本机、容器或 VPN 访问外部同号端口的流量。
- IPv6 默认采用按本项目 DNAT 连接和目标端点限制的 masquerade，保证目标回包经过 VPS；不生成全局 IPv6 masquerade。
- 同号端口段保留端口，异号端口段保持顺序映射；TCP 和 UDP 的映射结果必须一致。
- IPv6 原生转发需要 IPv6 forwarding；跨族内核路线还要分别检查宿主机和专用命名空间所需的 IPv4/IPv6 forwarding。

### 2.2 跨地址族：Jool 内核转换

普通 nft DNAT 只承担同地址族的地址/端口改写；IPv4 与 IPv6 包格式转换交给 Jool。已采用 Stateful NAT64：IPv6 主动访问走动态绑定，IPv4 主动访问 IPv6 服务走预建静态 BIB。后者需要显式生成映射。[Jool NAT64 教程](https://www.jool.mx/en/run-nat64.html)、[静态 BIB](https://www.jool.mx/en/bib.html)

采用两个专用 network namespace 和 veth，分别隔离两个方向的实例，避免 IPv4 主动连接策略与 IPv6 动态出站池互相影响。宿主机仅把匹配本项目入口的流量引入：

```text
客户端 → VPS 本机入口 → 宿主 nft（原始来源白名单 + 同族 DNAT）
       → 专用 veth → [专用 netns：Jool 内核转换]
       → 宿主 nft（限定出口 SNAT）→ 目标服务器
回复   ← 对应 nft conntrack 与 Jool session 的反向路径
```

符号：`P6` 为本项目转换前缀，`Q4` 为私有 IPv4 转换池，按实例分别分配。应用前检查与已有路由、Docker、VPN 和其他转换器不冲突。下列组合路径已通过真实 TCP/UDP 验证。

| 方向 | 入口处理 | Jool 转换 | 出口与回程 |
|---|---|---|---|
| IPv6 → IPv4 | 匹配 VPS 本地 IPv6 及端口，按顺序 DNAT 到 `P6` 中编码的 IPv4 目标及目标端口，保留客户端来源用于过滤 | NAT64 将客户端 IPv6 映射为 `Q4` 动态端点，目标还原为 IPv4 | 私有 `Q4` 出口按需 SNAT 成 VPS IPv4；返回先撤销该 SNAT，再经 Jool 及入口 conntrack 撤销 DNAT |
| IPv4 → IPv6 | 匹配 VPS 本地 IPv4 及端口，DNAT 到 `Q4` 专用服务端点 | 静态 BIB 将该端点映射到 IPv6 服务，IPv4 客户端来源转换为 `P6` 中的表示 | 转换前缀无法在公网回程时，限定 SNAT 成 VPS 可达 IPv6；返回先撤销 SNAT，再经 Jool 与入口 conntrack 返回 IPv4 客户端 |

实现时解决的映射与路由问题：

- 分别生成 TCP、UDP 的 pool4 和静态 BIB；端口段保持等长和顺序，不依靠 DNAT 随机选端口。静态服务池与动态分配池分离，防止地址/端口互相占用。[pool4 配置](https://www.jool.mx/en/usr-flags-pool4.html)
- BIB 两侧的传输端点在同一协议表内需唯一。多个入口指向同一个 IPv6 目标端点时，为每条声明分配独立的虚拟 IPv6 端点，再由宿主 nft 改写到真实目标，避免重复注册冲突 BIB。[BIB 配置约束](https://www.jool.mx/en/usr-flags-bib.html)
- 双向流量经过同一受管实例及对应 conntrack；补齐 `P6`、`Q4`、veth 中转网段的双向路由。私有池 + 限定 SNAT 已在现有双栈 VPS 验证，不要求额外申请公网 IP。
- IPv4 主动建连所需的 Jool 外部发起连接/地址依赖过滤设置必须显式管理，并由外层 nft 限制入口及回复端点；不能只添加 BIB 就视为可用。[Jool 过滤参数](https://www.jool.mx/en/usr-flags-global.html)
- TCP 双向传输、半关闭、超时和重传，以及 UDP 多客户端、连续响应、会话回收、大包、校验和、分片和 ICMP/ICMPv6 错误转换都需真实流量验证。此处评估包级转换，不再采用代理读缓冲或 worker 配置。

### 2.3 白名单放在转换命名空间外

Jool 的 Netfilter 转换路径会跳过所在命名空间的 `FORWARD`。实现中在宿主机向专用 veth 转发之前检查原始来源，不能依赖转换器内部的普通 forward 链完成白名单。[Jool hooks 与隔离建议](https://www.jool.mx/en/intro-jool.html)

- 宿主机只允许经过本项目入口规则标识、地址族/端口和白名单校验的连接进入转换器，不只凭 `ct status dnat` 判断归属。
- 直接访问转换前缀、私有池或经 Docker/VPN 绕入 veth 的流量默认拒绝；转换后的出口只允许配置目标和对应回复，不把该 namespace 变成开放 NAT64 网关。
- 独立 namespace 的正常 `FORWARD` 路径默认拒绝；当模块缺失、实例暂停或包未被转换而落回正常转发路径时，丢弃这些包，防止原样绕行或在宿主与 namespace 之间形成路由环。
- 实例、veth、路由和流量标识全部具有明确归属，不覆盖 WireGuard/Docker 已用标记；不把 Jool 的全局接管实例直接挂在宿主默认 namespace。

SIIT 作为对照评估：无状态地址映射本身不提供本项目所需的完整端口段和任意 IPv6 客户端汇聚能力，若改用它，需另外设计 nft 状态 NAT、地址映射与回程；本计划不把 SIIT 当成可直接替换 Stateful NAT64 的实现。

### 2.4 环境前置条件与持久化

- 跨族功能额外要求允许加载匹配当前内核的 Jool 模块，并具备 namespace、veth、netlink、必要路由及两族 forwarding 权限。当前项目的“Linux ≥ 5.2”不足以证明跨族后端可用；普通受限容器 VPS 可能无法满足。
- 实施时核对官方稳定发行版及目标内核，固定源码/软件包和校验值，确保用户态工具与模块匹配。旧介绍页的兼容表不作为新内核保证；目前核查到的稳定发行版为 v4.1.15，仍需逐个验证本项目环境。[官方发行记录](https://github.com/NICMx/Jool/releases/tag/v4.1.15)
- 旧版低 MTU UDP 验证发现问题后，将跨族最低版本设为 4.1.15，并限定在 4.1 系列；工具、磁盘模块和已加载模块必须一致。
- 评估发行版包或 DKMS、当前内核 headers、模块签名/Secure Boot、SELinux 及内核升级后的重建；不通过关闭安全机制或擅自更换 VPS 内核来绕过不兼容。
- 只用同族规则时不安装或加载 Jool。模块不兼容时，给出具体诊断并拒绝新增跨族规则，保留已有同族功能，不能回退到常驻用户态中继。
- 开机使用专用 `Type=oneshot` / `RemainAfterExit=yes` 控制单元恢复 namespace、过滤、路由、池及静态 BIB，执行完即退出。业务路径由内核处理，无需常驻用户进程；不启用不需要的同步守护进程。[Jool 持久化说明](https://www.jool.mx/en/run-persistent.html)
- `active (exited)` 只说明初始化命令已结束，状态查询仍须检查实际模块、实例、映射和路由，不能仅看 systemd 单元颜色。

## 3. 配置、校验与操作方式

### 3.1 兼容旧配置

保留 `/etc/port_forward_nft.conf` 作为声明配置。旧三字段始终表示 IPv4 入站 → IPv4 目标；新条目增加显式入口地址族，目标地址族由严格校验后的 IP 确定。禁止根据目标地址族猜测入口地址族。

已实现的格式如下，新版同时读取旧三字段和新四字段：

```text
# nft-sh-forward-format: 2
# 旧规则继续有效：IPv4 → IPv4
8080|203.0.113.10|80
# IPv6 → IPv6
ipv6|10000-10002|2001:db8:2::10|20000-20002
# IPv6 → IPv4
ipv6|11000|203.0.113.10|8080
# IPv4 → IPv6
ipv4|12000|2001:db8:2::10|8080
```

上述格式只适用于 v2.1.0 分支，不可粘贴到 v2.0.0 使用；示例地址仅用于说明。新功能首次写入前备份旧配置。回退旧脚本时必须同时恢复旧格式配置并撤销本项目转换实例和引流；旧脚本不能读取新条目。

内部转换前缀、地址池、namespace/veth 名称及分配记录另存本项目部署配置，先检查冲突再固定，重启和回滚复用同一分配。用户声明规则仍写真实目标，不要求用户手工填写内部映射；生成的 Jool JSON 由声明与部署参数重建，导入配置不得作为 shell 代码执行。

### 3.2 参数与冲突校验

- 扩展 `validate_target_ip`、`parse_forward_line`、`list_forwards`、冲突检测和全部调用方，统一携带入口族、目标族、端口段和选定后端。
- IPv6 目标首版支持全局单播和 ULA；规范化地址，拒绝未指定地址、回环、组播、链路本地、IPv4-mapped、带作用域标记的地址、CIDR 和域名，避免入口族歧义。
- 同入口地址族不允许端口段重叠；不同入口族可复用同一端口，需显式匹配报文族，并通过本地 socket、入口映射及内部池冲突检查。内核路径不创建用户态监听 socket。
- 检查 TCP、UDP、IPv4、IPv6 本地监听及通配监听，避免 nft 引流抢占其他服务入口。保留 SSH 端口保护，基础 IPv6 协议不得被引入转换器；不再引入代理 worker 或 `reuseport` 配置。
- 识别可发现的目标回流到本机入口的组合，拒绝自转发循环。导入、手工改配置后的 `apply` 和交互添加使用同一套校验。

### 3.3 菜单与 CLI

保留旧调用的 IPv4 → IPv4 语义；已增加可选的 `--listen-family ipv4|ipv6`，参数表示入口报文地址族，不表示创建监听进程：

```bash
bash nft.sh add-forward --listen-family ipv6 10000 2001:db8:2::10 20000
bash nft.sh add-forward --listen-family ipv6 11000 203.0.113.10 8080
bash nft.sh add-forward --listen-family ipv4 12000 2001:db8:2::10 8080
bash nft.sh del-forward --listen-family ipv6 11000
```

菜单明确显示入站族、目标族、TCP+UDP、映射及后端。按端口删除遇到两个地址族都有规则时必须要求指定族或规则编号，不能默认删除两条。

`status` 区分声明规则条数、nft 状态、Jool 模块/工具版本、各 namespace/实例、pool4/转换前缀、静态 BIB、路由及 forwarding 状态，必要时查询 session 和丢包计数。`print-rules` 保持只读、免 root、无副作用，并明确只展示 nft 部分；新增完整计划预览入口，展示拟生成的 Jool 配置、依赖、地址池、路由和 sysctl，不在预览时安装模块或创建资源。

## 4. 白名单、IPv6 网络和运维边界

### 4.1 白名单始终匹配原始入口来源

| 流量 | 过滤位置 | 使用的白名单 |
|---|---|---|
| IPv4 → IPv4 | nft forward，沿用现状 | `allowed_ips` |
| IPv6 → IPv6 | nft forward，按 DNAT 连接限制 | `allowed_ips_v6` |
| IPv6 → IPv4 | 宿主 nft forward，进入转换 veth 且改写来源之前 | `allowed_ips_v6` |
| IPv4 → IPv6 | 宿主 nft forward，进入转换 veth 且改写来源之前 | `allowed_ips` |

来源白名单在协议转换或来源 NAT 之前检查；不以内部池来源替代真实客户端来源，也不依赖 Jool 所在 namespace 的 `FORWARD`。宿主入口即使已经做了 DNAT，源地址仍需在此保留并验证。白名单开关、当前 SSH 来源检查和已有连接的处理保持现有语义；关闭白名单不等于开放任意地址转换。

优先验证方案中，目标端默认看到 VPS 的目标族出站地址，由限定 SNAT 保证回程；内核转换保留 TCP/UDP 业务内容，不插入 PROXY protocol，也不承诺目标收到真实客户端源 IP。诊断需能关联原始入口、内部绑定及最终目标。

### 4.2 IPv6 forwarding 与 RA

按规则需求在宿主机和转换 namespace 启用并持久化 IPv4/IPv6 forwarding；同时记录 IPv4 `rp_filter` 等可能影响 veth 回程的设置，必要调整仅限已确认需要的接口。开启前记录实际接口、地址、路由、forwarding 与 `accept_ra` 设置；对依赖 RA 学习地址或默认路由的上联接口，验证需要的 `accept_ra=2` 等设置，只调整本次需要管理的接口。不能全局套用设置，也不能只测当时还能连通，必须等 RA 更新后及重启后再次验证。[Linux 内核 sysctl 文档](https://docs.kernel.org/networking/ip-sysctl.html)

保留必要 ICMPv6、邻居发现和 DHCPv6；验证 PMTU、IPv6 扩展头与回程。检查内核能力、可用 IPv6 地址和到目标的路由；受限容器或缺少路由时给出具体原因。

### 4.3 应用、持久化与回滚

快照已从三个声明配置及本项目 nft 表扩展到转换资源、部署参数、持久化文件、oneshot 状态和受管 sysctl：

1. 只读预检声明、端口、路由/地址池冲突及工具/模块能力；生成候选配置，记录部署参数、受管实例配置与静态映射、veth/路由、oneshot 单元状态和将修改的 sysctl。
2. 在任何网络变更前启动独立回滚保护，并加锁防止并发 `apply`、删除或导入互相覆盖。
3. 先建立外层过滤和未转换包的拒绝路径，再准备隔离实例、池及静态 BIB；确认完整后才启用宿主入口引流，不能出现无保护的转换窗口。
4. 校验 nft、各实例、映射、双向路由和持久化配置一致后，再完成交互确认；任一阶段失败都返回非零并恢复。
5. 未确认、SSH 断开或控制命令被终止时，先封闭或撤销新引流，再按依赖顺序恢复旧实例配置、静态 BIB、路由、本项目 nft 表、文件及本次修改的 sysctl。保护规则恢复失败时须先断开转换路径，再执行 SSH 恢复措施。
6. 启动单元须先加载必要过滤与隔离资源，最后开放引流；加载失败时跨族入口保持不可达。重建实例可能丢失动态 BIB/session 及现有 TCP/UDP 状态，回滚只承诺恢复配置和新建连接能力，不能声称恢复原连接的内存状态。

nft 与 Jool 各自的批量配置能力不组成跨系统事务；路由、namespace、文件和 sysctl 按阶段恢复。实测 Jool 的文件更新会忽略 BIB 部分，因此声明改变时重建专用实例；仅修改白名单且实例、池、映射和路由完整时不重建。[Jool 原子配置](https://www.jool.mx/en/config-atomic.html)

导出只保存声明规则及经过定义的转换部署参数，不导出模块、动态 session 或任意 systemd 文件；导入严格限制成员类型、路径和重复项，校验本机地址池冲突后重建资源。清空转发和卸载撤销本项目引流、实例、veth、路由、生成文件及 oneshot 单元；不删除其他 Jool 实例，不盲目卸载共享模块或关闭其他程序使用的全局 forwarding。

## 5. 实施步骤与完成标准

以下阶段已完成实现和核心功能验收，执行顺序优先保证两种 IPv6 入站。详细测试矩阵按实际运行结果记录；特定内核、签名环境或容量结论不能从其他环境推断。

| 阶段 | 工作 | 完成标准 |
|---|---|---|

## 6. 测试矩阵

| 类别 | 验收范围与扩展矩阵 |
|---|---|

| 白名单与隔离 | IPv4/IPv6 单 IP、CIDR、非白名单拒绝、开关切换、当前 SSH 来源保护；从公网、Docker/VPN 直接访问转换前缀、私有池和 veth 均不能绕过；非指定目标回复和未转换包被拒绝 |

| IPv6 网络 | ICMPv6/邻居发现、RA 更新后的默认路由、重启后地址和路由、出站源地址选择、无可用 IPv6 时的明确失败 |
| 冲突与兼容 | 旧三字段无损读取、配置备份/降级恢复、双族同端口、本地通配监听、SSH 端口、非法 IPv6、回流目标、导入和手工配置校验；转换网段/标记冲突、多个入口共享目标、静态与动态池不互抢 |
| 故障恢复 | nft 预检/加载失败、Jool 模块/headers/权限缺失、工具版本不匹配、实例暂停、BIB 缺失、池耗尽、路由丢失、持久化失败、超时未确认、SSH 断开、并发操作和恢复本身失败 |

| 性能与规模 | 保存同族 nft 基线与跨族内核转换的吞吐、延迟、CPU、内存、BIB/session 数、端口段规模及池耗尽表现；报告实测范围，不预先承诺性能数值 |

在 netns 中用纯 IPv4、纯 IPv6 和双栈端点验证，不依赖公网提供商是否分配 IPv6；真实公网双栈测试另列记录。验证工具需扩展 `tests/echo_server.py` 的 IPv6 socket 支持，不把当前 IPv4 回显服务误算成 IPv6 验收。

保留并扩展 `tests/unit_test.sh`、`tests/netns_test.sh`、`tests/systemd_test.sh`、`tests/coexistence_test.sh` 和 `tests/reboot_test.sh`，新增独立的内核跨族测试。固定 Jool 版本并校验下载物；真实转换测试必须在已知内核、具备模块加载权限的 runner 或一次性虚拟机中执行，不能在普通容器中把不可加载模块的测试跳过后计为通过。

测试还需证明：控制命令结束后无用户态业务中继进程、无新增业务监听 socket，而四方向 TCP/UDP 仍能传输。本机访问自己的入口单独验证 output 引流和回复 conntrack，不用公网客户端用例代替。
